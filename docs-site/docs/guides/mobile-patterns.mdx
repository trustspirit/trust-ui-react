# Mobile patterns

trust-ui v2 is mobile-optimized, not just responsive: several of its rendering decisions depend on which *pointer* is in use, not just how wide the viewport is. This guide covers the mechanics — density vs. pointer, how `Table` behaves under 640px, safe areas, horizontal scroll, and why form inputs never trigger iOS's auto-zoom.

If you're looking for a specific component's mobile variant (`Dialog`'s sheet/fullscreen modes, `Menu`'s sheet mode, `DatePicker`'s native mode, and so on), that lives on the component's own reference page — this guide is about the cross-cutting mechanics underneath all of them.

## Density and pointer

`data-density` (`comfortable` default, or `compact`) controls control heights and padding — never color. It's meant for screens that are dense with data, set deliberately by the app, not detected from the device.

Pointer type is detected, not set, and it overrides density rather than combining with it. Under `@media (pointer: coarse)` — a finger or stylus, not a mouse — every control height snaps to `comfortable`-sized values or larger, regardless of which density is active:

| | `compact` | `comfortable` | `pointer: coarse` |
|---|---|---|---|
| `--tui-control-md` | 36px | 44px | 44px |
| `--tui-row-height` | 46px | 56px | 64px |

In other words, `compact` only actually shrinks controls on a mouse-driven surface. A touch device never sees a control smaller than its `comfortable` size, because 44px is the accepted minimum touch target — full table: [Spacing & Radius → Control heights](../design-tokens/spacing.mdx#control-heights).

Some interactive elements enforce a 44px floor directly rather than relying on the density variable alone, but not by the same mechanism. `Table`'s column-sort button sets an explicit `min-height: 44px` inside its own `@media (pointer: coarse)` rule — a second, belt-and-suspenders floor on top of the density table above, so the touch target holds even where the surrounding row is shorter. The mobile sort bar (below), by contrast, sets its `min-height: 44px` inside `@media (max-width: 640px)` only, with no `pointer: coarse` condition — it's 44px at that breakpoint regardless of pointer type, because the bar exists to be tapped and is sized for that unconditionally once the layout switches to summary cards.

## Table on mobile

Below 640px, `Table` has two independent behaviors, controlled by `mobileVariant`:

- **`"summary"` (default)** — each row collapses to a two-line card: primary label and its value on the first line, up to two secondary values and up to two "delta" (toned, directional) values split across the second line. The desktop `<thead>` disappears, since there are no more column headers to align with.
- **`"scroll"`** — every column stays, the table scrolls horizontally, and the first column sticks to the left edge as you scroll so you always know which row you're looking at.

Which column lands in which spot on the summary card is decided by `mobileSlot`. You can assign it explicitly per column (`'primary' | 'secondary' | 'value' | 'delta' | 'hidden'`); anything left unassigned is inferred — first non-numeric column becomes `primary`, toned numeric columns become `delta`, the last numeric column becomes `value`, and whatever's left fills `secondary` up to two slots, with the rest hidden. Full rule and the exact five-step order: [Table](../components/table.mdx#mobileslot-inference).

Because the summary mode hides the desktop header — and with it, the sortable column headers — `Table` renders a **mobile sort bar** in its place: a single full-width row naming the current sort column and direction, which opens the same sort control the header buttons would. It only appears in `"summary"` mode and only when at least one column is sortable; `"scroll"` mode keeps the real header, so it never needs a substitute.

⚠️ v1's default was equivalent to today's `"scroll"` — every column, no summary cards. Code migrated from v1 without setting `mobileVariant` explicitly changes behavior silently: rows that used to scroll horizontally now collapse into summary cards instead. There is no `"stacked"` value in v2 — pass `mobileVariant="scroll"` if you want the old all-columns behavior back.

## Safe areas

`--tui-safe-top/right/bottom/left` read `env(safe-area-inset-*)`, and fall back to `0px` on devices without a notch or home indicator — they're a no-op there, not an error. `<SafeAreaView>` applies them as padding on whichever edges you name.

A plain `--tui-safe-bottom` isn't quite enough for a bottom-pinned call-to-action: on a device with no inset at all, it would resolve to `0px` and the button would sit flush against the screen edge, out of comfortable thumb reach. `--tui-thumb-safe-bottom` covers that — `max(env(safe-area-inset-bottom, 0px), 16px)` — and it's what `<StickyFooter>` uses for its own bottom padding. Full token list: [Spacing & Radius → Touch targets & safe area](../design-tokens/spacing.mdx#touch-targets--safe-area).

## Horizontal scroll isolation

Any element that scrolls horizontally on a touch device risks handing that gesture to the browser instead — the page rubber-banding, or an edge swipe triggering back-navigation. `Table`'s scroll wrapper sets `overscroll-behavior-x: contain` for exactly this reason: the scroll stays contained inside the table once it reaches either end, instead of bleeding into the surrounding page.

If you're building your own horizontally-scrolling region, `trust-ui-react/styles.css` also ships a `.tui-scroll-container` utility class (`-webkit-overflow-scrolling: touch` for iOS momentum scroll, plus `overscroll-behavior: contain`) — add it to any scroll container rather than hand-rolling the same two declarations.

## The 16px input floor

iOS Safari zooms the whole page in when a focused `<input>`, `<textarea>`, or `<select>` has a computed font size under 16px — a jarring layout shift that has nothing to do with your design. trust-ui prevents it globally: under `pointer: coarse`, every `input`/`textarea`/`select` gets `font-size: max(16px, var(--tui-font-size-base))`, so the effective size is always at least 16px on a touch device no matter what `--tui-font-size-base` resolves to at the current density.

That base rule lives on a plain element selector, which is easy for a more specific rule to outrank without meaning to. `TextField`'s `sm` size variant is one such case — its class selector has higher specificity than the base rule, so `TextField` re-declares the same 16px floor locally for `sm` inputs and textareas rather than relying on the global rule alone. If you build your own compact form control, the same trap applies: a size variant with a class selector will silently win over the base `pointer: coarse` rule, so re-assert the 16px floor inside that variant too.

Full base-size scale, including how this interacts with density: [Typography → A second base-size token](../design-tokens/typography.mdx#a-second-base-size-token).

## Haptic feedback

trust-ui doesn't trigger haptic feedback by default, because there's no single web API for it: iOS Safari doesn't expose the Haptic Engine at all — only `navigator.vibrate()`, which Android supports and iOS Safari does not. `useHaptic` + `<HapticProvider>` give you the seam to plug in whatever's actually available:

```tsx
import { HapticProvider, useHaptic } from 'trust-ui-react';

// App root — wire a native bridge if you have one; otherwise the default
// falls back to navigator.vibrate() (Android) and is a no-op on iOS Safari.
<HapticProvider trigger={(type) => window.NativeBridge?.haptic(type)}>
  <App />
</HapticProvider>

function DeleteButton() {
  const haptic = useHaptic();
  return (
    <Button variant="danger" onClick={() => { haptic('warning'); confirmDelete(); }}>
      Delete
    </Button>
  );
}
```

`HapticType` is `'light' | 'medium' | 'heavy' | 'success' | 'warning' | 'error'` — no numbered "impact" scale, no `'selection'` type; each name maps to one built-in vibration pattern in the default `navigator.vibrate()` trigger, which a custom `trigger` is free to reinterpret however the target bridge expects.

## Touch-aware hooks

Reach for these when a component swaps behavior by input device — not for purely visual hover styling, which should stay in `@media (hover: hover)` CSS so it doesn't force a re-render. All are SSR-safe.

- **`useTouchDevice()`** — `true` when `(pointer: coarse)` matches. Re-evaluates if the input device changes mid-session (e.g. a mouse plugged into a tablet).
- **`useVisualViewport()`** — subscribes to `window.visualViewport`, returns `{ height, offsetTop, keyboardOpen }`. Powers `<KeyboardAvoidingView>`.
- **`useSwipe(ref, options)`** — 4-directional swipe detection with a configurable distance `threshold` (default 50px) and `velocity` (default 0.3 px/ms); both must be met to fire.
- **`useLongPress(ref, callback, options)`** — fires after holding `delay` ms (default 500), cancels if the pointer travels past `threshold` px (default 10). Powers `Tooltip`'s longpress mode.
- **`useDrag(ref, options)`** — pointer-events drag tracking, reports `offset` and end `velocity` per axis. Doesn't apply any transform itself. Powers `<BottomSheet>`'s drag-to-resize.
- **`useSnapPoints({ points, flingThreshold })`** — given a value and a list of snap points, returns the nearest target, or the next one over if velocity clears `flingThreshold` (a "fling"). Powers `<BottomSheet>`'s snap points.

## Testing on real devices

Viewport size is only part of mobile behavior — touch events, the on-screen keyboard, safe-area insets, and haptic feedback only behave correctly on a real device or a fully simulated one. Chrome DevTools' device mode simulates the viewport but not the touch event model or safe-area insets. For real coverage: connect an iPhone to Safari's Develop menu, use `chrome://inspect` for Android remote debugging, or a cloud device lab (BrowserStack, LambdaTest) for devices you don't own.
