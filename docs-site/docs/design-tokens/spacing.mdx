# Spacing & Radius

Spacing splits into two independent scales — one tied to density, one fixed — because they answer two different questions.

## Inner padding — density-linked

`--tui-pad-1` through `--tui-pad-4` size the space *inside* a control, between its border and its content.

| Token | `compact` | `comfortable` (default) |
|---|---|---|
| `--tui-pad-1` | 4px | 6px |
| `--tui-pad-2` | 8px | 10px |
| `--tui-pad-3` | 12px | 14px |
| `--tui-pad-4` | 16px | 20px |

These move with density because the control they pad moves with density too: switching to `compact` shrinks `--tui-control-md` from 44px to 36px. If inner padding stayed fixed while the control shrank around it, the text inside would end up crowding the edge — the padding has to shrink in step with the box it's padding, or the proportions break.

## Outer gaps — fixed

`--tui-gap-1` through `--tui-gap-6` size the space *between* elements — the layout-level spacing a page is built from.

| Token | Value |
|---|---|
| `--tui-gap-1` | 4px |
| `--tui-gap-2` | 8px |
| `--tui-gap-3` | 12px |
| `--tui-gap-4` | 16px |
| `--tui-gap-5` | 24px |
| `--tui-gap-6` | 32px |

These stay fixed regardless of density, and that's the deliberate half of the split: if gaps moved with density the way padding does, flipping a screen from `comfortable` to `compact` would reflow the entire page layout — every section spacing, every stack gap — all at once. An app author choosing `compact` for a dense data screen wants tighter controls, not a page whose overall composition shifts unpredictably underneath them. Padding is allowed to follow the control it belongs to; layout gaps are not allowed to follow anything but their own fixed scale.

## Radius

Four steps, unrelated to density:

| Token | Value | Usage |
|---|---|---|
| `--tui-radius-tight` | 4px | Small chips, tags |
| `--tui-radius-control` | 6px | Buttons, inputs |
| `--tui-radius-sheet` | 10px | Dialogs, panels, cards |
| `--tui-radius-full` | 9999px | Pills, avatars, dots |

## Control heights

`--tui-control-sm/md/lg` and `--tui-row-height` live in the density layer, alongside `--tui-font-size-base` (see [Typography](./typography.mdx#a-second-base-size-token)):

| Token | `compact` | `comfortable` (default) | `pointer: coarse` |
|---|---|---|---|
| `--tui-control-sm` | 30px | 36px | 36px |
| `--tui-control-md` | 36px | 44px | 44px |
| `--tui-control-lg` | 44px | 52px | 52px |
| `--tui-row-height` | 46px | 56px | 64px |

On a touch device (`pointer: coarse`), heights snap to the `comfortable` values or larger regardless of which density is set — `compact` only actually shrinks controls on a mouse-driven surface. This guarantees a minimum touch target on touch hardware no matter what an app author configures for density.

## Touch targets & safe area

Carried over unchanged — iOS notch and home-indicator insets:

| Token | Value |
|---|---|
| `--tui-safe-top` | `env(safe-area-inset-top, 0px)` |
| `--tui-safe-right` | `env(safe-area-inset-right, 0px)` |
| `--tui-safe-bottom` | `env(safe-area-inset-bottom, 0px)` |
| `--tui-safe-left` | `env(safe-area-inset-left, 0px)` |
| `--tui-thumb-safe-bottom` | `max(env(safe-area-inset-bottom, 0px), 16px)` — bottom padding for thumb-reach CTAs |

Use `<SafeAreaView>` and `<StickyFooter>` to apply these without writing custom CSS.
