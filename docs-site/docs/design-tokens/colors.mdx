# Colors

trust-ui v2 splits color into three layers. Each layer has exactly one job, and components only ever read from the last one.

1. **Palette** (`--tui-p-*`, `src/styles/palette.css`) — raw color values. No meaning, no theme-awareness. Components never reference this layer directly.
2. **Theme** (`src/styles/themes/light.css`, `dark.css`) — maps the palette onto `--tui-paper`, `--tui-ink`, `--tui-rule`, and the rest, once per theme.
3. **Semantic** (what components consume) — the theme output above, `data-theme="light"` or `data-theme="dark"` on an ancestor selects which mapping applies.

If you're overriding a color, override the semantic token (`--tui-ink`, `--tui-danger`, …) under `[data-theme='...']`, not a palette value — palette values aren't part of the contract components rely on.

## The achromatic core

The neutral palette is hue 0, saturation 0 — pure grayscale, `--tui-p-neutral-0` (white) through `--tui-p-neutral-1000` (black), with `--tui-p-neutral-950`/`900`/`850`/`800` filling in the dark end. Every surface, text, and rule token in both themes is one of these neutrals; no hue is mixed in.

## Surface

| Token | Light | Dark | Usage |
|---|---|---|---|
| `--tui-paper` | `--tui-p-neutral-0` | `--tui-p-neutral-950` | Page background |
| `--tui-sheet` | `--tui-p-neutral-0` | `--tui-p-neutral-950` | Panels, dialogs — same as paper in both themes; separation comes from `--tui-rule`, not a lighter/darker fill |
| `--tui-field` | `--tui-p-neutral-50` | `--tui-p-neutral-900` | Inputs, wells — the one surface that is deliberately a step off paper |

## Text

| Token | Usage |
|---|---|
| `--tui-ink` | Primary text, and the default value of `--tui-accent` |
| `--tui-ink-2` | Secondary text, labels |
| `--tui-ink-3` | Tertiary / de-emphasized text |
| `--tui-on-ink` | Text drawn on a solid `--tui-ink` fill (e.g. a filled button) |

## Rule

| Token | Usage |
|---|---|
| `--tui-rule` | Default divider / border |
| `--tui-rule-strong` | A border that needs to read as a stronger separation than `--tui-rule` — this is also how visual hierarchy is built without shadows. See [Elevation](./elevation.mdx). |

## State colors

| Token | Fills a surface? | Usage |
|---|---|---|
| `--tui-danger` (+ `--tui-danger-hover`, `--tui-on-danger`) | Yes | Destructive actions, error surfaces |
| `--tui-success` | No — text/border only | Positive status text |
| `--tui-warning` | No — text/border only | Caution status text |

`--tui-success` and `--tui-warning` are single tokens each, not scales — they color text and borders and never fill a background. Filling a background with saturated color is `--tui-danger`'s job alone; that's why it's the only state color with a hover step and an "on" (foreground-on-fill) counterpart.

## Accent

| Token | Default | Usage |
|---|---|---|
| `--tui-accent` | `var(--tui-ink)` | Brand color, if an app has one |
| `--tui-on-accent` | `var(--tui-on-ink)` | Text/icon on a filled accent surface |
| `--tui-accent-hover` | `var(--tui-ink-2)` | Hover state for accent-filled elements |

Out of the box there is no brand hue — accent resolves to ink, so a fresh install reads as pure grayscale. An app that wants a brand color overrides these three tokens; nothing else needs to change.

## Market colors — optional layer

Rise/fall/gain colors are not part of the default bundle. Apps with financial screens opt in:

```ts
import 'trust-ui-react/market.css';
```

This adds `--tui-rise` and `--tui-fall`, resolved from the market convention set by `data-market` on an ancestor element:

| `data-market` | Rise | Fall |
|---|---|---|
| `kr` (default) | red (`--tui-p-rise-*`) | blue (`--tui-p-fall-*`) |
| `us` | green (`--tui-p-gain-*`) | red (`--tui-p-rise-*`) |

Both themes are covered — `market.css` also carries dark-mode variants of each mapping. Without importing this file, `--tui-rise`/`--tui-fall` are undefined; nothing falls back to a default market.

## Two rules

- **Color carries meaning, chrome stays neutral.** Borders, dividers, and non-semantic surfaces are always drawn from the achromatic core. If a color shows up in the UI, it should be because something needs that color to convey a state or a value — not for decoration.
- **The color of a figure lives on the text; the color of danger lives on the fill.** Rise/fall/gain color numbers, never their container. Danger is the one state color allowed to paint a background. Nothing else does.
