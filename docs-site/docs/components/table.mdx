# Table

A data table with sorting, custom cell rendering, a total row, and a narrow-viewport summary layout.

## Sortable Columns

Set `sortable` on a column to make its header a button. Clicking cycles ascending → descending → unsorted. Empty values always sort to the end, regardless of direction.

## Numeric columns and tone

Set `numeric: true` to right-align a column (its header follows). All values in the table already render with tabular figures, whether or not a column is numeric — `numeric` only controls alignment, and `align` overrides it if you set both.

`tone` colors the cell's text to signal direction. `'auto'` reads the sign of the value — a leading `-` or a parenthesized value like `(3,584,000)` reads as negative, everything else positive, and `0` reads as neutral. You can also pass a function `(value, row) => 'rise' | 'fall' | 'neutral'` for custom logic (e.g. comparing against a threshold instead of zero).

The rise/fall colors themselves only exist if the app imports `trust-ui-react/market.css`. Without it, `--tui-rise` and `--tui-fall` are undefined and the cell falls back to the ordinary ink color — nothing breaks, the color simply doesn't appear. And the color only ever lands on the cell's text, never on a background, badge, or border.

## Custom rendering

`render(value, row, index)` replaces the default (which just prints the value). It runs **once per column per row** — the result is reused for both the desktop cell and, when that column lands in the mobile summary layout, the summary card. Because of that sharing, `render` must be a pure function: no side effects, and no reliance on anything other than its arguments. If it read from outside state or triggered a side effect, calling it once instead of twice (as the desktop-only rendering used to) would silently change behavior between the wide and narrow layouts.

In a `summaryRow` (see below), `index` is `-1` — that's the signal that this call is the total row, not a data row.

<ComponentPreview code={`<Table
  columns={[
    { key: 'name', header: 'Name' },
    { key: 'done', header: 'Status', render: (value) => (value ? '✓ Done' : '— Pending') },
  ]}
  data={[
    { name: 'Ship docs', done: true },
    { name: 'Write tests', done: false },
  ]}
/>`}>
  <Table
    columns={[
      { key: 'name', header: 'Name' },
      { key: 'done', header: 'Status', render: (value) => (value ? '✓ Done' : '— Pending') },
    ]}
    data={[
      { name: 'Ship docs', done: true },
      { name: 'Write tests', done: false },
    ]}
  />
</ComponentPreview>

## Row click is pointer-only

`onRowClick` is a pointer convenience, not a way to make the row an interactive control. `<tr>` outside a `role="grid"` table is not an interactive element, so the Table deliberately does **not** make the row focusable, and there is no `onKeyDown` handling on it. A sighted mouse user can click anywhere in the row; a keyboard or assistive-technology user cannot activate it at all through the row itself.

If a row needs to be reachable without a pointer, put a real control — a `<button>` or a link — inside one of its cells via `render`. That control is focusable and operable on its own, and `onRowClick` can stay as an additional convenience for pointer users on top of it.

```tsx
<Table
  columns={[
    { key: 'name', header: 'Name' },
    {
      key: 'id',
      header: '',
      render: (_value, row) => <a href={`/users/${row.id}`}>Open</a>,
    },
  ]}
  data={users}
  onRowClick={(row) => navigate(`/users/${row.id}`)}
/>
```

## Summary row

`summaryRow` closes the table with a total row, styled with the table's heaviest rule above and below it (the same convention a financial statement uses to bracket a total). It reuses the same `columns` and the same `render` functions as the body rows — there's no separate summary renderer.

Because `summaryRow` is typed as `Partial<T>`, any field you don't include is `undefined`. Its column's `render` still gets called — the total row calls every column's cell exactly like a body row would — so a `render` that reads a field directly (rather than through its `value` argument) needs to handle that field being missing. What appears in that cell (blank, `'—'`, or something else) is `render`'s decision. The `index` argument is `-1` for every cell in this row, which is how `render` can tell "this is the total, not row 0."

<ComponentPreview code={`<Table
  columns={[
    { key: 'name', header: 'Item' },
    { key: 'qty', header: 'Qty', numeric: true },
    { key: 'total', header: 'Total', numeric: true, render: (value) => value == null ? '—' : \`$\${value}\` },
  ]}
  data={[
    { name: 'Widget', qty: 3, total: 30 },
    { name: 'Gadget', qty: 1, total: 45 },
  ]}
  summaryRow={{ name: 'Total', total: 75 }}
/>`}>
  <Table
    columns={[
      { key: 'name', header: 'Item' },
      { key: 'qty', header: 'Qty', numeric: true },
      { key: 'total', header: 'Total', numeric: true, render: (value) => value == null ? '—' : `$${value}` },
    ]}
    data={[
      { name: 'Widget', qty: 3, total: 30 },
      { name: 'Gadget', qty: 1, total: 45 },
    ]}
    summaryRow={{ name: 'Total', total: 75 }}
  />
</ComponentPreview>

Note that `qty` has no `render` and is missing from `summaryRow` — its cell in the total row renders `undefined`, i.e. blank. Only `total`'s `render` guards against the missing value.

## Sticky header

`stickyHeader` pins the header row while the table's own content scrolls (the table needs a bounded, scrollable ancestor for this to have an effect — for example a wrapper with a fixed `height` and `overflow: auto`).

```tsx
<Table stickyHeader columns={columns} data={longDataset} />
```

## Mobile layout

`mobileVariant` controls what narrow viewports get:

| Value | Behavior |
|---|---|
| `'summary'` (default) | Each row collapses into a two-line summary card. Column headers disappear; sorting moves into a tap-to-open sheet. |
| `'scroll'` | All columns are kept and the table scrolls horizontally. The first column stays pinned (`position: sticky`) so you always know which row you're looking at. |

:::caution v1 default changed
v1 defaulted to `'scroll'`. Code migrated from v1 without setting `mobileVariant` compiles cleanly in v2 but silently changes behavior on narrow screens — instead of every column staying visible via horizontal scroll, only four slots (primary/value/secondary/delta) remain and the rest of the columns disappear from view. Set `mobileVariant="scroll"` explicitly to keep the old behavior.
:::

### mobileSlot inference

In `'summary'` mode, each row becomes a two-line card with four regions: a **primary** label, a **value**, up to two **secondary** items, and up to two **delta** items. Every column lands in one of those four regions, or is hidden, per its `mobileSlot`.

You can set `mobileSlot` (`'primary' | 'secondary' | 'value' | 'delta' | 'hidden'`) on any subset of columns — partial assignment is the common case: promote the one column you care about, and let the rest fall out by inference rather than annotating all of them. Unassigned columns are resolved in this order:

1. **Explicit assignment wins first.** Any column with a `mobileSlot` set is placed by that value before inference runs. `'hidden'` is a placement too — it removes the column from the pool inference draws from, the same as any other explicit slot. `'secondary'` and `'delta'` each hold at most two columns; an explicit assignment past that limit is simply dropped (the column ends up unplaced, i.e. invisible in the summary), so a third explicit `mobileSlot="delta"` column will not appear.
2. **`primary`** — if still unset, the first remaining non-numeric column is picked (falling back to the first remaining column of any kind if every remaining column is numeric). This is meant for a name, a title, whatever identifies the row.
3. **`delta`** (up to 2) — remaining numeric columns that also have a `tone` other than `'none'` are picked, in declaration order, up to two. This is meant for columns that carry a direction, like a change value.
4. **`value`** — if still unset, the *last* remaining numeric column is picked (falling back to the last remaining column of any kind if none are numeric). This is meant for the number closest to "the result" — typically the rightmost numeric column in the declaration.
5. **`secondary`** (up to 2) — whatever is still left is filled in, in declaration order, until the two-item cap is reached. Anything beyond that cap is not shown on narrow viewports at all.

Because step 2 and step 4 both fall back to "whatever's left" when there's no numeric column to prefer, a table with only text columns still gets a sensible `primary`/`value` split rather than leaving both empty.

<ComponentPreview code={`<Table
  columns={[
    { key: 'symbol', header: 'Symbol' },
    { key: 'name', header: 'Company' },
    { key: 'price', header: 'Price', numeric: true },
    { key: 'change', header: 'Change', numeric: true, tone: 'auto' },
  ]}
  data={[
    { symbol: 'AAPL', name: 'Apple', price: '182.40', change: '+1.85%' },
    { symbol: 'MSFT', name: 'Microsoft', price: '412.10', change: '-0.42%' },
  ]}
/>`}>
  <div style={{ maxWidth: 360 }}>

      columns={[
        { key: 'symbol', header: 'Symbol' },
        { key: 'name', header: 'Company' },
        { key: 'price', header: 'Price', numeric: true },
        { key: 'change', header: 'Change', numeric: true, tone: 'auto' },

In this example, no column sets `mobileSlot`. Inference resolves it as: `symbol` becomes `primary` (first non-numeric column), `change` becomes `delta` (numeric with a `tone`), `price` becomes `value` (last remaining numeric column), and `name` becomes `secondary` (whatever's left). Resize the preview or open it on a narrow viewport to see the two-line card layout.
